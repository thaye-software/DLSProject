---------- Everyday setup start ----------

Use this section after the first deploy below has already succeeded.
First install: softwareToInstall.txt is the previous step. Skip to First-time setup.

Normal PowerShell, from the repo root.

1. Open Docker Desktop. Wait until Kubernetes is green.

2.
kubectl version --client
kubectl config current-context
kubectl get nodes

Expected: v1.36.1, context docker-desktop, node docker-desktop Ready.
If the client is older, follow softwareToInstall.txt.

3.
kubectl get pods

Expected, each 1/1 Running: rabbitmq, catalog-db, catalog, orders-db, orders, payment, notif, search-db, search-cache, search, messaging-db, messaging, users-db, users, auth.
The first time, search-db or messaging-db can stay ContainerCreating while mongo:7 downloads.

4.
curl.exe http://localhost:30002/health
curl.exe http://localhost:30000/health
curl.exe http://localhost:30006/health
curl.exe http://localhost:30007/health
curl.exe http://localhost:30003/health
curl.exe http://localhost:30004/health
curl.exe http://localhost:30005/health
curl.exe http://localhost:30001/health

Each line should be {"status":"ok"}.
RabbitMQ UI: http://localhost:31672  guest / guest

5. Open Lens. Bottom bar: docker-desktop (v1.36.1).
Namespace default. Workloads lists the same fifteen pods.
An empty Overview metrics panel is normal.
"Node docker-desktop has been rebooted" is from startup.

6. If an app pod is ErrImagePull or ImagePullBackOff, see why:

kubectl describe pod -l app=catalog

"unauthorized" or "denied": that image is still private on GHCR. Make it public, see First-time setup, then delete the pod:
kubectl delete pod -l app=catalog

"not found" or "manifest unknown": that service has no published image yet. CI publishes one on every push to dev or main that changes the service.

Use the matching app name: catalog, orders, payment, notif, search, messaging, users, or auth.

To run the newest image CI published, restart the deployment. It pulls :latest again:
kubectl rollout restart deployment/catalog

7. If kubectl get pods lists nothing, apply again in this order:

kubectl apply -f kubernetes/rabbitmq
kubectl apply -f kubernetes/catalog
kubectl apply -f kubernetes/orders
kubectl apply -f kubernetes/payment
kubectl apply -f kubernetes/notif
kubectl apply -f kubernetes/search
kubectl apply -f kubernetes/messaging
kubectl apply -f kubernetes/users
kubectl apply -f kubernetes/auth

Then repeat steps 3 and 4.


---------- First-time setup ----------

softwareToInstall.txt is done. Do the rest once, in a normal PowerShell, from the repo root.
Come back to Everyday setup start on the next morning.

Open Docker Desktop and wait until Kubernetes is green.

kubectl version --client
kubectl config current-context
kubectl get nodes

Expected: v1.36.1, context docker-desktop, node docker-desktop Ready.

This starts fifteen workloads, in this order:
RabbitMQ, Catalog and its Postgres, Orders and its Postgres, Payment, Notif, Search with MongoDB and Redis, Messaging and its MongoDB, Users and its Postgres, then Auth.

Kubernetes pulls each app image from GitHub Container Registry: ghcr.io/thaye-software/dlsproject-<service folder>:latest.
CI pushes these images on every push to dev or main, after the tests and the security scan pass. Nothing is built on this PC.
Apply one folder at a time. The kubernetes folder also contains these text guides, so leave the folder itself out of kubectl apply.
Usernames, passwords, the fake payment provider, the fake mailer, and the fake Supabase stand-ins for Users and Auth are already in the yaml files.

The images are public, so Kubernetes pulls them without a login.
A service's first image on GHCR starts out private. An owner of the thaye-software organization makes it public once:
GitHub, thaye-software, Packages, the dlsproject-<service> package, Package settings, Change visibility, Public.

If an app pod stays ErrImagePull or ImagePullBackOff, run kubectl describe pod -l app=catalog and see step 6 of Everyday setup start.
Use the matching app name: catalog, orders, payment, notif, search, messaging, users, or auth.
Wait until the health check in that section prints {"status":"ok"} before you start the next section.


---------- RabbitMQ ----------

Start here. The public image is rabbitmq:4-management.
Catalog, Orders, Payment, Notif, Search, Messaging, and Users connect to rabbitmq:5672 with guest / guest.

kubectl apply -f kubernetes/rabbitmq
kubectl rollout status deployment/rabbitmq
kubectl get pods -l app=rabbitmq

The pod should be 1/1 Running.
Open http://localhost:31672 and sign in as guest / guest.
From this PC, AMQP is localhost:30672. Other pods use the name rabbitmq.


---------- Catalog ----------

Start after RabbitMQ is Running.
Catalog keeps products, stock, and reservations in its own Postgres. Other services call it over HTTP.

kubectl apply -f kubernetes/catalog
kubectl rollout status deployment/catalog-db
kubectl rollout status deployment/catalog

The Catalog image applies its database migrations, then listens. The first start can take a minute.
curl.exe http://localhost:30002/health

Expected: {"status":"ok"}
Postgres from this PC is localhost:30434. Other pods call http://catalog:3002.


---------- Orders ----------

Start after Catalog returns {"status":"ok"}.
Orders keeps reserved orders in its own Postgres and calls Catalog at http://catalog:3002.
The shipping price is 300 DKK.

kubectl rollout status deployment/orders-db
kubectl rollout status deployment/orders

The Orders image applies its database migrations, then listens.

---------- Payment ----------

Start after Orders returns {"status":"ok"}.
Payment has no database. It calls Orders at http://orders:3000 and uses the fake provider, so this cluster needs no Stripe key.
The image is ghcr.io/thaye-software/dlsproject-payments:latest, built from microservices/payments.

---------- Notif ----------

kubectl logs deployment/notif

---------- Search ----------

Start after RabbitMQ is Running.
Search fills its product read model from catalog events on RabbitMQ, and stores that model in MongoDB with a cache in Redis. The image is ghcr.io/thaye-software/dlsproject-search:latest.
Redis has no disk. A restart clears the cache, and searches still run.

kubectl apply -f kubernetes/search
kubectl rollout status deployment/search-db

The first mongo:7 download can take about ten minutes. The pod stays ContainerCreating during that download.
If rollout status stops waiting, the download is still going. Check again with:
kubectl get pods -l app=search-db

When search-db is 1/1 Running:
kubectl rollout status deployment/search-cache
kubectl rollout status deployment/search
curl.exe http://localhost:30003/health
curl.exe "http://localhost:30003/search"

Health should be {"status":"ok"}.
An empty list is expected. Catalog does not publish new products onto this queue yet. See DECISIONS.md.
A typical body is {"items":[],"page":1,"page_size":20,"total":0}.
Mongo from this PC is localhost:30018. Redis from this PC is localhost:30380. Other pods call http://search:3003.
kubectl logs deployment/search
The log should include: search listening on port 3003 (cache: redis)


---------- Messaging ----------

Start after Catalog returns {"status":"ok"}. RabbitMQ must already be Running.
Messaging stores chat in its own MongoDB and calls Catalog at http://catalog:3002. It reads user_deleted from RabbitMQ.
Supabase Realtime is left unset, so live broadcast is off and chat history still works over HTTP.

kubectl apply -f kubernetes/messaging
kubectl rollout status deployment/messaging-db

mongo:7 is the same image Search uses. The first download can take about ten minutes. The pod stays ContainerCreating during that download.
If rollout status stops waiting, the download is still going. Check again with:
kubectl get pods -l app=messaging-db

When messaging-db is 1/1 Running:
kubectl rollout status deployment/messaging
curl.exe http://localhost:30004/health

Expected: {"status":"ok"}
Mongo from this PC is localhost:30019. Other pods call http://messaging:3004.
kubectl logs deployment/messaging
The log should include: messaging listening on port 3004 (realtime: off)


---------- Users ----------

Start after RabbitMQ is Running.
Users keeps profiles, roles, and the saved address in its own Postgres, and publishes user_deleted on RabbitMQ (Orders, Catalog, and Messaging read it).
IDENTITY_PROVIDER is fake, so this cluster needs no Supabase project. Supabase accounts and avatar files are never touched, and avatars get a made-up URL.

kubectl apply -f kubernetes/users
kubectl rollout status deployment/users-db
kubectl rollout status deployment/users

The Users image applies its database migrations, then listens.
curl.exe http://localhost:30005/health

Expected: {"status":"ok"}
Postgres from this PC is localhost:30435. Other pods call http://users:3005.
kubectl logs deployment/users
The log should include: users listening on port 3005


---------- Auth ----------

Start after Users returns {"status":"ok"}.
Auth has no database. The gateway will ask it at /verify whether a caller is signed in. It looks up the role at http://users:3005.
TOKEN_VERIFIER is fake, so this cluster needs no Supabase project: the bearer token fake:<user id> signs in as that user, unchecked. Only use it in this local cluster.

kubectl apply -f kubernetes/auth
kubectl rollout status deployment/auth
curl.exe http://localhost:30001/health

Expected: {"status":"ok"}
kubectl logs deployment/auth
The log should include: auth listening on port 3001 (token verifier: fake)
Other pods call http://auth:3001.

Try a sign-in. There is no gateway yet, so call Auth and Users directly. A user with no profile is stopped:
curl.exe -i -H "Authorization: Bearer fake:11111111-1111-4111-8111-111111111111" -H "X-Forwarded-Method: GET" -H "X-Forwarded-Uri: /users/me" http://localhost:30001/verify

Expected: HTTP/1.1 403 and "code":"profile_required" (the first time only; after the next step it is 200).
Create the profile, as the gateway would after /verify:
Invoke-RestMethod -Method Post http://localhost:30005/users -ContentType application/json -Headers @{ 'X-User-Id' = '11111111-1111-4111-8111-111111111111'; 'X-User-Email' = '11111111-1111-4111-8111-111111111111@fake.invalid' } -Body '{"username":"k8s_check"}'

Expected: the new profile, with role customer.
Run the first curl.exe again. Expected: HTTP/1.1 200 with X-User-Role: customer.
