Catalog service contract
=======================
Audience: Orders, Search, Messaging, Editorial, Auctions, and the API gateway.
Catalog owns products, stock, and reservations in PostgreSQL.
It publishes catalog.events. Search is the only consumer of that exchange.

It does not own sessions, user profiles, conversations, blog posts, auctions,
payments, mail, the search index, exchange rates, VAT, orders, or negotiated
offer prices.

Field lists for HTTP live in microservices/docs/contracts/openapi.yaml.
Field lists for events live in microservices/docs/contracts/asyncapi.yaml.
This file says what Catalog does. If a field here and a YAML schema disagree,
the YAML wins and this file should be corrected.

Transport
  HTTP/JSON for calls. RabbitMQ for events, one exchange per publisher.
  Catalog's exchange is catalog.events (topic).
  Delivery is at least once. Consumers are idempotent on the CloudEvents id.
  Product, brand, and availability events also carry an aggregate version.
  A consumer ignores an event whose version is not newer than the one it stored.

Conventions
  Ids Catalog creates (reservation_id, CloudEvents id) are UUID v4.
  order_id is the UUID Orders sends. Orders derives it; Catalog does not.
  Timestamps are ISO-8601 UTC, such as 2026-10-14T10:00:00Z.
  Payload fields are snake_case. Schemas reject unknown fields on the way in.
  Consumers ignore fields they do not know.
  Money is { amount_minor, currency }. amount_minor is an integer in øre.
  1 DKK = 100. Catalog prices use currency DKK. Never a float. VAT is not
  calculated; the listed price is final.
  Errors are application/problem+json: type, title, status, detail, instance.
  type is https://limitedwatches.dk/problems/<code>.
  Callers branch on the HTTP status. A reservation 409 also includes
  unavailable_product_ids (UUID array).
  Availability is available, reserved, sold, or hidden.
  hidden means the product is not visible.

  RabbitMQ messages are persistent, content type application/cloudevents+json.
  The publisher waits for a broker confirm. Each consumer queue is a durable
  quorum queue named <consumer>.<exchange>, with x-dead-letter-exchange = dlx
  and a queue <queue>.dlq. A handler that throws is retried 5 times, waiting
  1s, 2s, 4s, 8s, and 8s, then dead-lettered. A body that is not a CloudEvent,
  or whose data does not match the event type, is dead-lettered without those
  retries. The handler acks only after its database transaction commits.

Auth
  Catalog does not parse end-user Supabase tokens.
  The gateway verifies those and may forward X-User-Id, X-User-Role
  (admin or customer), X-User-Email, and traceparent. Catalog accepts those
  headers only from the gateway.

  GET /products/{product_id} is public. No login.

  /internal/* is service-to-service. The gateway does not route it.
  The caller signs an HS256 JWT with the shared INTERNAL_JWT_SECRET and sends
  Authorization: Bearer. Claims: iss = calling service, aud = catalog,
  iat, exp at most 60 seconds later. Catalog checks the signature, aud, exp,
  and that iss is a caller it expects. Otherwise 401 problem+json.
  Orders uses iss = orders.

HTTP
----

GET /health
  200 { status: "ok" } when PostgreSQL and RabbitMQ are both reachable.
  503 problem+json otherwise: database_unavailable or broker_unavailable.
  Same shape as Orders.

GET /products/{product_id}
  Public. Also used by Messaging, Editorial, and Auctions.
  A hidden product is still 200, with availability hidden.
  200 ProductSummary:
    product_id, name, slug, brand_name, model, price, availability,
    thumbnail_url
  brand_name, model, and thumbnail_url may be null.
  404 problem+json when the id does not exist.
  The body has no serial_number and no internal_id.
  Auctions may call this. How a watch on auction is held is not decided
  (DECISIONS.md item 7). An auction win might not reserve here
  (DECISIONS.md item 2). This contract does not define either one.

POST /internal/reservations
  Orders only. Service JWT, iss = orders.
  Header Idempotency-Key is a UUID and must equal order_id.
  Body:
    order_id
    items[]: product_id, quantity (>= 1, one or more lines)
    expires_at
  All lines reserve or none do. Catalog decrements stock by each quantity.
  The 201 prices are Catalog's list prices. Orders does not send a price.
  201 Reservation:
    reservation_id, order_id, status (active), items, expires_at, created_at
    each item: product_id, product_name, quantity, unit_price, thumbnail_url
  Orders copies product_name, thumbnail_url, and unit_price onto the order
  line. Later edits in Catalog do not change that copy.
  The 201 items are exactly the requested product ids and quantities.
  Orders compares them to the request and, on a mismatch, fails the save
  and calls DELETE. Catalog does not add, drop, or resize a line.
  Idempotent on order_id. The same order_id returns the first reservation
  and does not decrement again, even if the new body differs.
  A missing Idempotency-Key, a key that is not a UUID, a key that is not
  order_id, or an illegal body: 422 problem+json, code validation_error,
  title Invalid request, stock unchanged. Orders treats any status other
  than 201, 200, and 409 as a failure and tells the customer to retry, so
  these requests must not be 500.
  409 problem+json, code out_of_stock, with unavailable_product_ids, and no
  stock change, when any line is missing, hidden, sold, or short of stock.
  Orders treats every 409 as unavailable.
  The first success writes product_availability_changed, reason order_reserved.
  correlationid and order_id are the order id. subject is the product id.
  causationid is null, because the cause is this HTTP call, not an event.
  A repeat does not write the event again.
  expires_at is stored as Orders sent it. Orders sets it to 30 minutes after
  the order is created. Catalog does not replace that timestamp.
  Catalog itself releases a reservation still active at expires_at plus 5
  minutes. That covers Orders being down. Orders' own expiry is the normal
  path and runs at expires_at, five minutes earlier.

DELETE /internal/reservations/{order_id}
  Orders only. Service JWT, iss = orders.
  Only for the rollback when Orders reserved and then failed to save the order.
  It releases only an active reservation.
  204 when this call releases the stock, when it was already released, when
  it is already confirmed, and when the order id is unknown. Confirmed and
  unknown do not change stock.
  A real release writes product_availability_changed, reason order_released,
  with the same correlation id and subject rules as reserve, causationid null.
  Normal cancel and expiry do not use this call. They use order events.

Stock
-----
  stock on the product is the sellable count. Reserve decrements it by the
  line quantity. Confirm does not decrement again.
  Availability is reserved while at least one unit is held by an active
  reservation.
  It is sold when a reservation is confirmed and the sellable stock is 0.
  It is available when nothing is held and the sellable stock is greater
  than 0. Confirming one unit of a product that still has stock left
  therefore ends as available, not sold.
  Releasing adds those reserved quantities back, once per reservation.
  A later DELETE, safety-net pass, order_expired, or second delivery of the
  same event does not add them again.
  version on the product starts at 1 and increases by 1 on each of these
  changes. The event carries the new version and the previous availability.

Events Catalog publishes
------------------------
Exchange catalog.events. Routing key = CloudEvents type.
Envelope on every event: specversion 1.0, id (uuid), source /services/catalog,
type, time, datacontenttype application/json, subject (the aggregate id),
dataversion 1, correlationid, causationid (nullable), data.
Search binds one queue, search.catalog.events, plus search.catalog.events.dlq.

product_created
  data: product (ProductSnapshot), changed_by (user uuid)
  Search inserts the listing.

product_updated
  data: product (ProductSnapshot), changed_by, changed_fields
  changed_fields names top-level ProductSnapshot fields, for example price
  or description. At least one.
  Search replaces the document.

product_deleted
  data: product_id, version, deleted_by, deleted_at
  Search removes the listing.

product_availability_changed
  data: product_id, version, availability, previous_availability, stock,
        reason, order_id (nullable), changed_at
  reason is order_reserved, order_released, order_confirmed, or admin_update.
  Search shows available, reserved, or sold.

brand_updated
  data: brand (brand_id, name, slug), version, changed_by, changed_at
  Search updates the brand name and slug on listings with that brand_id.

ProductSnapshot is the full product state. Consumers do not call Catalog
back to fill it in. Fields: product_id, version, product_type, name,
description, price, stock, visible, availability, watch, images, created_at,
updated_at. watch may be null.
WatchDetails is public watch data: watch_id, brand, model, slug, reference,
year, condition, size_mm, movement, glass_type, limited, box, papers,
bracelet_type, bracelet_color, dial_color. serial_number and internal_id
are never published.
ProductImage: image_id, url, is_thumbnail.
Brand on a watch: brand_id, name, slug.

The HTTP that creates, updates, or deletes a product or a brand is not in
the OpenAPI file. Do not invent it here. The five events above are still
the ones Search consumes once that HTTP exists.
admin_update is a legal reason on product_availability_changed. The admin
call that would cause it is not specified.

Events Catalog consumes
-----------------------
Queue catalog.order.events on exchange order.events, plus
catalog.order.events.dlq. Idempotent on the CloudEvents id, stored with the
stock change. Also idempotent on the reservation: stock moves once, even
when the safety net and an event both run.

The quantities put back are the ones stored on the reservation, which are
the lines Orders copied from the 201. An event whose order id has no
reservation is acknowledged and changes nothing. That includes an auction
win if it never reserved (DECISIONS.md item 2 is still open).
correlationid on the availability event is the order id. causationid is
the CloudEvents id of the order event. subject is the product id.

order_confirmed
  Applies only to an active reservation. Mark it confirmed and publish
  product_availability_changed, reason order_confirmed. Stock is not
  decremented again. Already released or already confirmed: change nothing.
  Availability then follows the stock rules above.

order_cancelled
  Returns the reserved quantities once, including when the reservation was
  already confirmed. A customer cancel is only from RESERVED, so that
  reservation is still active. An admin cancel of a paid order (PENDING
  through DELIVERED) publishes order_cancelled with was_paid true, and the
  stock must come back from sold. Publish reason order_released.
  Orders does not send order_cancelled after RETURNED: the stock already
  came back on order_status_changed, and a second event would add it twice.

order_expired
  Returns the stock only when the reservation is still active. Same event
  as a release, reason order_released.

order_status_changed
  Put stock back only when previous_status is PENDING, PROCESSING, SHIPPED,
  or DELIVERED and status is RETURNED or REFUNDED. Other transitions do not
  change stock. REFUNDED after RETURNED does not match that previous_status,
  so it does not add stock a second time.
  Catalog acts only when this event arrives. DECISIONS.md item 4 is open:
  a system refund has no user id for changed_by, and Orders then publishes
  nothing. Catalog does not gain a second release call for that case.

Queue catalog.user.events on exchange user.events, plus
catalog.user.events.dlq, routing key user_deleted.
The favorites that deletion would clear are not specified yet. Until they
are, this consumer has no fields and no effect to implement.

What each neighbour does
------------------------

Orders
  Calls POST /internal/reservations and, only to roll back a failed save,
  DELETE /internal/reservations/{order_id}.
  Publishes order_confirmed, order_cancelled, order_expired, and
  order_status_changed. Catalog never calls Orders.
  One reservation may hold several products, and a line quantity may be
  greater than 1.

Payment
  Does not call Catalog and does not consume catalog.events.
  The charged amount is the price Orders copied at reserve time, or an
  offer price Orders accepted. Catalog is not told the offer and does not
  check what was captured.

Notif
  Does not call Catalog and does not consume catalog.events.
  The confirmation email is filled from order_confirmed, which already
  carries the copied product name and thumbnail.

Messaging and Editorial
  May call GET /products/{product_id}. A 404 means the product is gone.
  They keep their own copy of whatever they render. Catalog does not store
  messages or posts.

Search
  The shopfront calls Search for text search, not Catalog.
  Search consumes all five catalog.events. It does not write catalog data.
  price, stock, visibility, and availability come from the latest event.

Auctions
  May call GET /products/{product_id}.
  DECISIONS.md item 7 is open, so this contract does not say whether an
  auction reserves stock or the product becomes hidden.
  DECISIONS.md item 2 is open, so this contract does not say whether an
  auction win calls POST /internal/reservations.

Users
  Publishes user_deleted. Catalog does not read profiles, emails, or
  addresses.

Not specified yet
-----------------
No request or response fields for any of these. They are named so they are
not invented from an older draft.

  Favorites. The contracts README says Catalog owns them and would delete
  them on user_deleted, and would delete them when a product is deleted.
  There is no favorite HTTP and no favorite payload in the YAML.

  Admin writes that create, update, or delete products and brands.
  The events those writes would publish are specified above. The HTTP is not.

  Image upload and Supabase Storage. An event may carry ProductImage.url.
  How the blob is stored is not a contract.

  The Cloud AI provider named on the architecture diagram.
